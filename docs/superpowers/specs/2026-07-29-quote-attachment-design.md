# 기안·품의 견적서 첨부 설계

작성일 2026-07-29 · 대상 모듈 `approvals` (기안·품의)

## 문제

결재 시스템인데 증빙이 체크박스뿐이다.

지금 있는 것:

| 있는 것 | 실체 |
| --- | --- |
| `meta.draft.attachments: string[]` | LLM이 쓴 **붙임 목록 문구** ("견적서 비교표 및 사업자등록증 각 1부") |
| `meta.attachmentsChecked: number[]` | 작성자가 누른 **체크박스** |
| `meta.quotes: {vendor, amount}[]` | 견적 업체·금액 (폼 3칸, 최저가 순 정렬) |
| `Document.attachments Json?` | 스키마에 자리만 있고 아무도 안 씀 |

결재자가 승인 버튼을 누를 때 손에 쥔 증거는 "작성자가 견적서 있다고 체크했다"뿐이다. 감사에서 증빙이 되지 않는다.

빠진 것은 정확히 하나다 — **`meta.quotes`의 각 업체 줄에 실물 파일이 안 붙는다.**

## 이미 있어서 새로 만들지 않는 것

- **견적 비교표 데이터** — `quotes: {vendor, amount}[]`가 이미 폼에 있고, LLM 프롬프트에 들어가 본문에 반영된다.
- **수의계약 2인 견적 강제** — `actions.ts`가 이미 `cls.context === "direct" && quotes.length < 2`로 초안 생성을 막는다.
- **첨부 규칙 판정** — `rules.ts`의 `Classification.context`가 그대로 답이다. 새 규칙 엔진 없음.

## 결정 사항

| 항목 | 결정 |
| --- | --- |
| 필수 범위 | **금액 있는 품의만 차단.** `context === "none"`(예산 없음)은 강제하지 않는다 |
| 저장 위치 | **DB 별도 테이블.** 외부 오브젝트 스토리지는 500단지 넘어갈 때 |
| 용량 절감 | **브라우저에서 리사이즈 후 업로드** (서버 부담 0) |
| 긴급 예외 | **넣는다.** 사유를 적으면 상신되고, 그 사유가 결재자 화면에 뜬다 |

## 설계

### 1. 스키마 — 테이블 하나

```prisma
model DocumentAttachment {
  id         String   @id @default(cuid())
  documentId String
  document   Document @relation(fields: [documentId], references: [id], onDelete: Cascade)
  /// meta.quotes 배열 위치 — 어느 업체의 견적서인가.
  /// null = 업체에 매이지 않는 문서 단위 첨부 (입찰 건의 추정가격 산출근거 등)
  quoteIndex Int?
  name       String
  mime       String
  size       Int
  /// 사후 위변조 검증 — "결재 당시 그 파일이 이것인가"
  sha256     String
  /// 문서 폐기(void) 시 null — 이름·해시는 기록으로 남고 용량만 회수한다
  data       Bytes?
  createdAt  DateTime @default(now())

  @@index([documentId])
}
```

- **`Document.attachments` Json을 쓰지 않는 이유:** Json에 base64를 넣으면 문서를 읽을 때마다 파일이 통째로 딸려온다. 목록 쿼리가 죽는다. 별도 테이블이면 `data`를 select 하지 않는 한 안 딸려온다.
- **unique 제약을 걸지 않는 이유:** 업체 견적서가 여러 장(폰 사진 2~3장)일 수 있다. 업체당 최대 3장, 문서당 최대 9장을 코드에서 제한한다.
- **`onDelete: Cascade`** — 단지 탈퇴 시 `purgeExpiredTenants`의 `document.deleteMany`가 자동으로 딸린 첨부까지 지운다. 그 함수는 수정하지 않는다.

### 2. 업로드 — 브라우저가 줄인다

관리사무소 직원은 업체 견적서를 **폰으로 찍는다.** 4032×3024, 5MB다. 그대로 받으면 안 된다.

- **이미지:** canvas로 장변 2000px, WebP q0.8 재인코딩 → 5MB 사진이 약 250KB (20배). 라이브러리 0개, 서버 부담 0.
  - 2000px = A4 스캔 기준 약 171 DPI. 견적서 표의 작은 글씨까지 읽힌다.
- **PDF:** 리사이즈 불가. 그대로 받되 3MB 상한. (업체가 메일로 보내는 PDF는 보통 100KB~1MB)
- **서버 액션으로 받는다** — 이 코드베이스의 모든 폼이 서버 액션이다. 라우트 핸들러를 따로 두지 않는다 (아래 "함께 고치는 것" 참조).
- **서버에서 재검증한다** (클라이언트를 믿지 않는다): mime 화이트리스트(`image/*`, `application/pdf`), size, 문서 소유권(`tenantId`), 문서 상태(draft·rejected만).

### 3. 열람 — `GET /api/attachments/[id]`

세션을 확인하고 `attachment.document.tenantId === session.tenantId`를 확인한 뒤 스트림한다. **여기가 신뢰 경계라 게으르게 하지 않는다** — 이 확인이 없으면 id만 알면 남의 단지 견적서를 읽는다.

### 4. 강제 — 기존 가드 옆 한 줄

`submitDocument`(상신)에서 `cls.context`로 갈린다:

| `context` | 뜻 | 요구 |
| --- | --- | --- |
| `direct` | 수의계약 (VAT제외 500만 이하) | **입력된 업체 전부, 각각 1장 이상** (업체는 이미 2곳 이상이 강제돼 있다) |
| `bid` | 500만 초과, K-apt 전자입찰 | **문서 단위 첨부 1장 이상** (`quoteIndex = null`) |
| `none` | 예산 없음 | 강제하지 않음 |

- `direct`에서 "각각"인 이유: 파일 2장을 한 업체에 몰아 올려도 2인 견적 요건은 충족되지 않는다.
- **"입력된 업체 전부"인 이유:** 견적 비교표에 실린 금액은 전부 증빙돼야 한다. 업체를 3곳 적어놓고 2곳만 증빙하면 나머지 한 줄은 검증되지 않은 숫자다. 3곳째 견적서를 못 받았으면 그 줄을 지우거나(업체는 2곳으로 줄어든다) 아래 긴급 예외를 쓴다.
- `bid`가 문서 단위인 이유: 전자입찰은 견적서를 받는 절차가 아니라 `quotes`가 비어 있을 수 있다. 매달 업체 줄이 없으므로 `quoteIndex = null`로 붙인다.

### 5. 긴급 예외

견적서를 아직 못 받았는데 상신해야 하는 상황이 실제로 있다. 막기만 하면 사용자는 아무 파일이나 올려서 뚫는다 — 그게 더 나쁘다.

```ts
meta.quoteWaiver?: { reason: string; byName: string; at: string }
```

- 상신 시 요구 장수가 부족하면 **사유 입력을 요구**하고, 사유가 있으면 통과시킨다.
- 사유는 **결재 패널(`ApprovalPanel`)에 눈에 띄게 표시**된다. 결재자가 "증빙 없음"을 알고 승인해야 의미가 있다.
- 사유는 상신과 함께 잠긴다(첨부와 같은 가드).
- 파일이 요구 장수를 채우면 판정에서 waiver는 쓰이지 않는다. 별도로 지우지 않는다.

### 6. 잠금 · 회수

- **상신 후 업로드·삭제·사유 수정 불가** — `status !== "draft" && status !== "rejected"`. `toggleGianAttachment`가 이미 쓰는 가드와 같다. 결재 중 견적서 바꿔치기를 막는다.
- **문서 폐기(`void`)** — `data = null`로 비우고 row는 남긴다. 결재 기록(누가 무엇을 승인했는가)은 보존하면서 용량만 회수한다.
- **단지 탈퇴** — `onDelete: Cascade`가 처리한다.

## 함께 고치는 것 — 서버 액션 body 한도

발견한 기존 버그. 견적서 첨부와 **같은 뿌리**라 같은 작업에서 고친다.

서버 액션의 요청 body 한도는 기본 **1MB**인데(Next 16.2.12 문서 `serverActions.md`), `next.config.ts`에 이 설정이 없다. 그런데 두 업로드가 그보다 큰 한도를 약속한다:

| 업로드 | 코드가 약속하는 한도 | 실제 통과 |
| --- | --- | --- |
| 직인 (`updateTenantInfo`) | 1MB | 1MB − multipart 오버헤드 |
| **세대 명부 엑셀 (`uploadUnits`)** | **5MB** | **1MB** |

`uploadUnits`는 "5MB 이하 파일만 업로드할 수 있습니다"라고 말하면서 1MB에서 막힌다. 액션이 실행되기도 전에 Next가 거절하므로 **그 메시지조차 나오지 않는다.** `MAX_UNIT_ROWS = 20000`짜리 명부가 이 경우다.

호출부마다 숫자를 깎는 것은 증상 처리이고, 엑셀은 깎으면 기능이 죽는다. 근본 수정은 한 줄이다:

```ts
// next.config.ts
experimental: { serverActions: { bodySizeLimit: "6mb" } }
```

**이 수정이 견적서 설계를 단순하게 만든다.** 원래 견적서 업로드를 라우트 핸들러로 두려던 유일한 이유가 "전역 한도를 올리기 싫어서"였는데, 엑셀 때문에 어차피 올려야 한다. 그러면 견적서도 이 코드베이스의 공통 문법인 서버 액션으로 받는 게 맞다.

## 안 만드는 것

| 항목 | 이유 |
| --- | --- |
| 인쇄물에 견적서 PDF 병합 | A4 격자가 깨진다. 화면에서 따로 인쇄 |
| 썸네일 생성 | 리사이즈된 250KB를 그대로 쓰면 된다 |
| 해시 중복제거 | 같은 견적서가 여러 문서에 붙는 일이 드물다 |
| 견적서 외 일반 첨부의 **UI**(사업자등록증·도면) | 저장 슬롯(`quoteIndex = null`)은 이번에 생긴다. 화면만 나중에 |
| 외부 오브젝트 스토리지 | 500단지 넘어갈 때. `data` → `url` 컬럼 교체가 이전 경로 |

## 용량 추정

| 항목 | 값 |
| --- | --- |
| 문서당 평균 (업체 2~3곳 × 1장 × 250KB) | 약 600KB |
| 문서당 최악 (9장) | 2.25MB |
| 단지당 월 (지출 품의 5건) | 약 3MB |
| **100단지 연간** | **약 3.6GB** |
| 500단지 연간 | 약 18GB |

100단지 수준이면 새 인프라 없이 DB로 충분하다. 그 위로 가면 `data` 컬럼을 `url`로 바꾼다.

## 성공 기준

구현이 끝났다고 말하려면 아래가 전부 확인돼야 한다.

1. **1.5MB 엑셀 업로드** — 수정 전 실패를 실제 앱에서 재현하고, 수정 후 같은 파일로 성공한다. *(현재 실패한다는 것은 Next 문서 근거이며 아직 재현하지 않았다 — 재현이 이 항목의 첫 단계다.)*
2. `npx tsx gian-attachment.test.ts` 통과 — `context`별 요구 장수 + waiver 판정 순수 함수.
3. 수의계약 품의에서 견적서를 1장만 올리고 상신 → 막힌다. 사유를 입력하면 통과하고, 결재 패널에 그 사유가 뜬다.
4. 5MB 사진을 올린 뒤 DB row 크기가 400KB 미만이다.
5. 다른 단지 계정으로 `/api/attachments/[id]`를 직접 호출하면 거부된다.
6. 상신된 문서에서 업로드·삭제 버튼이 사라지고, 서버 액션을 직접 호출해도 거부된다.
