# 설비·수선 이력 모듈 — 개발 프롬프트

> 이 문서를 새 세션에 그대로 주고 "이 프롬프트대로 구현해줘"라고 하면 된다.
> 구현 전 AGENTS.md와 아래 "먼저 읽을 파일"을 반드시 읽는다.
> 견본: 마스터 테이블+엑셀 업로드는 **세대 관리(설정 > 세대)**, 기록=Document는
> **법정점검 대장 스펙**(2026-08-05-legal-inspection-prompt.md)과 같은 문법.
> **이 모듈에는 법정 엔진도 LLM도 없다** — "기록이 쌓이는 구조" 자체가 상품이다.
> 세 스펙(법정점검·회의록·수선) 중 개발이 가장 가볍다.

## 1. 목표

소장 인력 부족 이유 **1위(63.7%) — 노후화로 인한 수선 수요 급증**에 대응한다.
30년 이상 단지의 28.5%가 직원 1~3명 — 모듈 단위 구독으로 소규모 단지에 진입하는
디벅의 확정 차별화 축과 가장 정확히 겹치는 고통이다.

고통 세 겹: ① 수선이 끝없이 밀려오는데 1~3명이 접수·업체 호출·확인·기록을 다 한다
② 수선 내역이 소장 수첩·기억·영수증 뭉치에 있어 소장 교체(3개월~1년 계약) 시
**인수인계가 불가능**하다 ③ 반복 고장 설비의 누계 수리비를 몰라 수리 vs 교체 판단도,
입대의에 교체 예산을 요구할 설득 자료도 없다.

한 줄 정의: **"수선 한 건을 30초에 기록하면, 설비별 이력·비용이 쌓여 인수인계
문서와 교체 설득 자료가 저절로 나온다."** 이 모듈의 산출물(설비 이력 카드)이
입대의 대응(고통 2위)의 무기가 되고 교체 품의(approvals)로 이어진다 — 모듈이
서로를 팔아주는 구조.

## 2. 확정된 설계 결정 (재논의 불필요)

- **별도 모듈 신설 확정 (2026-08-05, 사용자 결정 — facilities 통합 아님).** 근거:
  ① 구매 동기가 다르다(법정점검=과태료 방지 / 수선 이력=인수인계·예산 설득)
  ② 대상이 다르다(점검은 전 단지, 수선 폭증은 노후 단지) ③ 노후 소규모 단지가
  수선만 골라 구독할 수 있는 게 모듈 단위 구독 철학에 맞다.
  - 레지스트리 신규 등록: id `repairs`(가칭), 이름 "설비·수선 이력"(가칭 — 구현
    세션에서 사용자 확인), **아이콘 Wrench는 이 모듈이 가져간다**(수선에 더 어울림).
  - ⚠️ **`facilities` 정리가 세트다**: 법정점검 대장으로 재정의되는 facilities의
    아이콘을 다른 것으로 바꾸고(ShieldCheck 축 — `module-icons.ts` 매핑 확인), 설명
    문구에서 "수리 이력" 약속을 제거한다(동작을 바꾸면 문구도 같은 커밋 — AGENTS.md).
    두 모듈 중 먼저 구현되는 쪽 세션이 이 정리를 수행한다.
  - 가격 15,000~20,000원 축 — 구현 세션에서 사용자 확정. `isActive`는 완성 시 true
    (모듈 라우트 구현 전 true 금지 — 체험 소진 규칙).
- **마스터는 테이블, 기록은 문서** — 코드베이스의 결 그대로(세대 마스터·직원 명부는
  테이블, 증빙·기록은 Document).
  - `Equipment`(설비 대장) 테이블 신설. 폐기 설비는 **삭제가 아니라 비활성**(이력
    보존 — TrainingStaff 퇴사자와 같은 판단).
  - 수선 기록 = Document, 새 type `"repair"`, `docNoPrefixes`에 `수선` 추가.
    상태는 `Document.status`(`pending`=조치 중 → `completed`) — 할 일 위젯 컨벤션
    (type+status+dueDate)과 같은 축. 사진·영수증은 기존 문서 첨부 인프라.
- **설비 미지정 수선 허용**(`meta.equipmentId` null) — "복도 전등 교체" 같은
  잡수선에 설비 등록을 강요하면 기록 자체를 안 하게 된다. **기록 문턱이 낮은 게 이
  모듈의 생명.** 나중에 [설비에 연결] 버튼으로 잇는다.
- **채번은 저장 즉시**(`createDocument`) — 공지문·교육일지의 "완성 시점 채번"과
  다르다. 수선 기록에는 초안 단계가 없다(작문·검토가 없는 즉시 기록). draft 개념을
  들여오지 말 것.
- **수선 기록 폼은 모바일 한 손 입력이 명시적 요구사항** — 기록은 책상이 아니라
  지하 기계실에서 폰으로 한다. 사진은 폰 카메라 직접 촬영 업로드가 자연스러워야
  한다. (전용 앱 아님 — 반응형 웹에서.)
- **반복 고장 집계는 순수 함수** — 설비별 최근 12개월 횟수·누계 비용. 임계
  (12개월 3회 이상 또는 비용 상위)를 넘으면 모듈 홈에 경고 카드. 크론 없음 —
  열 때 계산(체험 만료 시점 비교와 같은 판단).
- **연동 2종은 상대 모듈 구독 시에만 노출**(`isSubscribed` 확인):
  ① 법정점검 대장(facilities)의 지적사항 있는 점검 기록 → [수선 등록] 버튼(지적
  내용이 증상으로 미리 채워진 폼) ② 설비 상세 → [교체 품의 만들기](approvals) —
  설비명·이력 요약을 meta로 상속해 기안 생성 폼으로. **장충금 판정·결재선은 gian
  규칙 엔진이 담당** — 이 모듈은 근거만 넘긴다(법 해석은 코드가 하지 않는다).
  facilities가 아직 미구현이면 ①은 그쪽 구현 세션의 몫으로 남긴다(스펙에 기록됨).
- **범위 밖 (다시 검토하지 말 것)**: 장기수선계획 수립·조정(별개의 큰 법정 도메인,
  아파트너스/AFMS 전문층 존재 — 디벅의 자리는 그들이 안 내려오는 소규모 단지의
  일상 수선 기록) / QR 설비 태그(하드웨어 접점 — 드롭다운으로 문턱 충분히 낮음,
  수요 확인 후) / 예방 정비 임의 주기(법정 주기는 facilities 소관 — 겹치면 두 모듈
  경계가 무너진다) / LLM(기록 모듈에 작문이 필요 없다).

## 3. 스키마

```prisma
model Equipment {
  id          String    @id @default(cuid())
  tenantId    String
  name        String    // "지하 1층 급수펌프 #2"
  category    String    // 승강기 | 급수·배수 | 전기 | 소방 | 난방·보일러 | 건축·외벽 | 조경·부대시설 | 기타
  location    String?   // 동·위치
  installedAt DateTime? // 설치·최근 교체 시점 (연 단위 입력 허용 — 1월 1일로 저장)
  vendor      String?   // 담당 업체·연락처 자유 텍스트
  note        String?
  active      Boolean   @default(true)
  tenant      Tenant    @relation(...)
  @@index([tenantId])
}
```

- ⚠️ tenant 탈퇴 purge(`src/lib/tenant-deletion.ts`)에 deleteMany 추가.
- Document meta: `{ equipmentId?, symptom, action, vendor, cost, startedAt,
  completedAt }`. 설비별 조회는 meta JSON 필터(`findNoticeFor` 선례) — 단지 규모
  (연 수백 건)에서 충분하다.
- Equipment 삭제는 없다(비활성만). equipmentId가 가리키는 설비가 비활성이어도
  기록 조회는 정상 동작해야 한다.

## 4. 흐름

**① 초기 설정 (1회)** — 설비 대장: 화면 등록 + **엑셀 업로드**(샘플 파일 제공).
과거 수선 이력도 엑셀 이관 지원 — **인수인계 가치는 과거 이력이 있어야 도입 첫날
부터 산다.** 업로드는 세대 업로드의 교훈 전부 적용: `$transaction` + `deleteMany`/
`createMany`(행별 루프 금지 — AGENTS.md), 행 상한(설비 2,000·이력 10,000), 헤더
오인 판정 주의("가동/나동" 버그 선례). 이력 이관은 삭제-재생성이 아니라 **추가만**
(기존 기록을 날리면 안 된다 — 세대와 다른 점, 주석으로 명기).

**② 수선 기록 (건당 30초)** — 설비 선택(검색 드롭다운, 건너뛰기 가능) → 증상 →
조치·업체·비용(PriceInput — `parseWon` 규칙) → 사진 → 저장(즉시 채번). 미완이면
`조치 중`, 완료 시점에 완료 처리(완료일 기록).

**③ 이력이 일하게 하기** — 설비 상세: 타임라인(수선 기록 시간순) + 12개월 횟수·
누계 비용 배지. 임계 초과 설비는 모듈 홈 경고 카드. [이력 카드 인쇄](A4) /
[교체 품의 만들기](approvals 구독 시).

## 9. 수용 기준

1. 설비를 고르고 증상·비용만 넣으면(나머지 기본값) **30초 안에 기록이 끝난다** —
   모바일 뷰포트에서 실제 입력 흐름 확인.
2. 설비 미지정 수선이 저장되고, 나중에 [설비에 연결]로 이어진다.
3. 저장 즉시 `수선-YYYY-####` 채번. 문서함 통합 검색에 걸린다.
4. 설비 상세에서 12개월 횟수·누계 비용이 정확하다 — 월 경계·미완료(조치 중) 포함
   여부를 순수 함수 테스트로 고정(`npx tsx repairs.test.ts`).
5. 임계 초과 설비가 모듈 홈 경고 카드에 떠오른다.
6. A4 이력 카드: 기록 5건 1장, 30건에서 표가 행 중간에서 잘리지 않는다(실측).
7. 엑셀 업로드: 설비는 교체(deleteMany+createMany), **과거 이력은 추가만** —
   재업로드해도 기존 수선 기록이 사라지지 않는다(테스트).
8. [교체 품의 만들기]는 approvals 구독 시에만 노출되고, 설비명·이력 요약이 기안
   폼에 미리 채워진다. 미구독이면 버튼이 없다(잠금 유도 배너 금지 — 홈/헤더 모듈
   종속 버튼 금지 규칙의 정신).
9. 비용 입력에 콤마를 넣어도 0원이 되지 않는다(`parseWon`).
10. tenant 탈퇴 purge가 Equipment를 지운다(테스트).
11. 시드: 신규 모듈 행 + **Wrench 아이콘 이관 + facilities 설명에서 "수리 이력"
    제거**가 같은 커밋에 있다(동작-문구 동기 규칙).
12. LLM 호출·`ANTHROPIC_API_KEY` 의존이 코드에 없다 — 전 기능이 키 없이 돈다.
